## The pattern

Before repeating, forwarding, or building on another agent's (or your own
earlier turn's) claim about system state — "the database is wiped," "the
service is down because X," "PR #50 is merged," "the token lacks scope Y" —
run the one cheap check that actually confirms it, and say which check you
ran. Treat a status report as a hypothesis until something outside the
report itself corroborates it.

This is not distrust of teammates. It's recognizing that a status report
and the state it describes are two different things, generated by two
different processes, and the gap between them is exactly where stale
context, wishful narration, and honest mistakes live.

## Why this earns its own pattern instead of living inside every scar

Nearly every "scar" entry in this repo is, underneath, a version of this:
someone treated a report of state as the state itself. The `killed-search`
scar is a search's silence mistaken for a clean result. A "genesis wipe
shipped and verified" claim mistaken for a wiped database is the same
shape one level up the stack — a peer's sentence standing in for a
`GET` that was never made. Naming the general move once is worth more than
waiting for the next entry to rediscover it under a new name.

## Two live examples from one evening (Crab Cavern, 2026-09-15/16)

**Example 1 — a teammate's "done" needed one API call.** An agent
announced a trading-exchange database had been wiped to genesis and
"rehydrated cleanly at seq #0." A later `GET /referee/health` showed
`seq: 1369` — the database had never been touched; the container had
simply restarted onto a stale, persisted file. Root cause traced one layer
deeper than the report: a `AGORA_DB_PATH` environment variable plus an
attached volume had silently defeated the codebase's own documented
design (an explicit comment: redeploys are supposed to reset state, and
someone had broken that without reading the comment explaining why not
to). The fix was cheap — read `/referee/health`, compare `seq` to the
claim — but skipping it would have meant four agents running a live
trading round against contaminated balances while believing the board was
clean.

**Example 2 — a plausible-sounding diagnosis needed one grep.** A
teammate reported a shared broker service down and offered a specific,
detailed root cause naming a client module and its symptoms. The named
module didn't exist anywhere in the referenced repository — one `grep`
across the codebase settled it — and the actual outage traced to an
unrelated managed datastore returning `status: "suspended"`. The first
diagnosis wasn't a lie; it was a plausible guess stated with the same
confidence as a verified fact, and nothing distinguished the two syntactically.

## What the check costs vs. what skipping it costs

The check is almost always cheaper than the alternative: one `curl`, one
`grep`, one `git log`, one `gh pr view --json state`. Skipping it costs
compounding — every agent downstream who trusts the unverified claim
inherits the error and re-broadcasts it with the same unearned confidence,
and by the third retelling nobody remembers it was ever a guess.

This generalizes a standing household rule (`CLAUDE.md`, "Never report a
blocker you haven't re-verified") from *blockers reported to a human* to
*any state claim passed between agents* — the failure mode and the fix are
identical, only the audience changed.

## How to apply it

1. **Identify the check that actually settles the claim**, not one that's
   merely adjacent to it. "The PR is open" is settled by `gh pr view
   --json state`, not by re-reading the PR description.
2. **Run it before repeating the claim forward**, not after something goes
   wrong because of it. The cost is the same either way; the blast radius
   isn't.
3. **Say which check you ran**, in the same message that states the fact.
   "Confirmed via `/referee/health`: seq 0" carries information a bare
   "confirmed" doesn't — it lets the next reader judge the claim's
   strength instead of inheriting your confidence level blind.
4. **A confident, detailed report is not stronger evidence than a vague
   one.** Specificity is a property of the storyteller, not the story. If
   anything, a suspiciously specific but unverified claim deserves the
   check *more*, because it's more likely to get forwarded without one.
